# Planning

把当前对话与项目上下文整理成最少但足够的规划工件，使工作具备实施条件。先确定各项事实的项目属主，再按需让产品合同与技术探索往返收敛；不为填满文档类型而创建工件。

## 1. 确定工作项

按项目文档分层与 Issue 配置定位本次 Proposal 或既有工作项，以 Issue 编号、URL 或文件路径标识。它负责本次目标、交付范围、产品行为与验收、评审和批准证据，并链接长期设计的属主。

复用合适的既有工作项；确实需要新的规划根节点时才创建 Proposal。创建或更新 Proposal 时读取 [proposal.md](./proposal.md)。

工作项直接写清本次产品行为、范围和验收；跨工作项持续生效的合同按需复用或建立独立 Spec。重要技术设计与决定写入项目登记的设计属主；采用 Agent Notes 的项目让 proposed Note 承载实施前设计评审，工作项从自身链接到 Note。同一设计只保留一个权威属主。

## 2. 收敛产品合同与技术设计

### Spec

产品行为、范围或验收需要跨工作项持续生效的独立属主时，读取 [spec.md](./spec.md)，创建或更新 Spec；否则由本次工作项写全。

Spec 是经评审接受后可直接指导实现与验收的行为合同，覆盖产品行为、标准、契约、协议、安全策略、兼容边界与运维不变量。Spec 修订记录只摘要合同变化，不记录理由或决策史。已有 PRD 可以作为背景输入，但不能代替本次明确合同。

### 探索性设计

当技术可行性会实质影响产品范围时，读取 [rfc.md](./rfc.md)，在已登记的设计属主中形成探索草案。采用 Agent Notes 的项目使用 proposed Note；已有独立 RFC 属主的项目沿用 RFC。

探索草案必须区分产品事实与临时假设，把影响产品范围的结论反馈给工作项或独立 Spec，不得作为实施依据。

产品合同与探索草案可以往返修改，直到范围与验收不再依赖未解决的技术可行性问题。

### 技术设计定稿

需要解决重要技术决定时，使用 [rfc.md](./rfc.md) 的设计检查项，把已确定的产品合同转成技术设计。设计写在项目选定的 Agent Note 或既有独立 RFC 中；一份产品合同可以由多个边界明确的设计分别承接。

设计定稿遵循 [技术设计规则](./rfc.md) 的合同稳定性与评审条件。Note 的 proposed/implemented 表示交付生命周期，不代替评审和批准证据。

使用项目既有领域语言和架构约束。规划形成或改变持久领域知识或架构决定时，使用 `domain-modeling` 判断是否需要记录；采用 Agent Notes 的项目更新或创建相关 Note，不为同一决定另建 ADR。

### 决定权限

在已同意的产品合同、既有架构和项目约束内，自主解决普通技术选择。

涉及未解决的产品、业务、兼容性、成本、风险、架构方向或其他价值判断时，交由用户决定，除非用户已经明确委托决定权。

## 3. Plan Review

必要规划内容形成后，读取 [review.md](./review.md) 执行 Plan Review。

把发现交回拥有它的工件：产品范围与验收问题回到工作项或独立 Spec，技术设计问题回到选定的 Note 或 RFC，工作状态与批准证据回到 Proposal 或工作项。

解决实质问题后重新评审。等待用户决定时继续推进不受影响的规划，但不得宣称整体通过。

## 4. 完成与交接

Planning 完成需要同时满足：

- 产品范围和验收条件已经稳定；
- 实施所需设计已按项目约定接受或批准；
- 设计完整承接适用的工作项产品合同或独立 Spec；
- 所需决定已解决；
- Plan Review 通过。

若用户只要求规划，交付规划结果与评审证据后结束。端到端任务继续进入项目的 Implementation Gate，并单独核对执行授权。
