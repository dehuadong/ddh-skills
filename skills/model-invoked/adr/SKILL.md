# 持久架构决定

当设计过程中重大架构决策逐渐明确时，先判断是否值得长期记录，再写入项目选定的决定属主。

## 资格条件

仅当以下三个条件全部满足时，才为架构决定单独建立持久记录：

1. **难以逆转** — 以后更改该决策具有有意义的成本
2. **脱离上下文会令人困惑** — 未来的读者很可能会合理地想知道为什么选择了这种方法
3. **是真实权衡的结果** — 存在真正的备选方案，并且基于特定原因选择了其中一个

如果任一条件不满足，则不为该架构决定单独建档；它仍可作为已有设计 Note 的一部分。

记录前先排除规范性行为、安全策略、协议和兼容要求（归工作项或独立 Spec），以及普通实现细节。技术设计及其决定由项目登记的 Agent Note 或既有 RFC 属主拥有。

架构形态、集成模式或技术选择只有在能说明长期反悔成本、真实可行备选、选择理由与接受的代价时才可能符合条件。边界、所有权或职责划分本身不构成单独建档的理由；必须证明改变它会造成有意义的迁移成本或锁定。

不要为本地实现细节、显而易见的决策或容易逆转的决策单独建档。

## 位置

先按项目工件约定确定决定的属主。采用 Agent Notes 的项目，在相关 proposed 或 implemented Note 中维护决定，遵循其格式与生命周期，不另建重复 ADR；已有权威 ADR 继续由它拥有。仅当项目选择独立 ADR 且尚未规定位置时，才使用 `docs/adr/` 作为后备位置。多上下文仓库按项目指令和上下文映射选择目录。

使用顺序编号：

`0001-slug.md`，`0002-slug.md`，...

对于包含多个上下文的代码库，将特定于上下文的 ADR 放在该上下文中，系统级 ADR 放在 ADR 根目录。

按需创建 ADR 目录。

## 编号

按项目约定与上下文映射确定 ADR 目录，扫描其中最大编号并加一。多上下文仓库若不同目录重复编号，引用时带上下文或路径以消除歧义。

## 格式

ADR 要简短，但必须把准入理由写具体。使用以下结构；“反悔成本”和“权衡”不可省略：

```md
---
status: proposed
---

# {决策标题}

## 背景

{触发该选择的约束或问题。}

## 决定

{选择了什么；引用相关产品合同与既有设计，不复制其中的正文。}

## 反悔成本

{改变决定时需要迁移什么，或会付出什么长期成本。}

## 权衡

{真实可行的备选、选择理由，以及接受的代价。}
```

无法具体填写“反悔成本”或“权衡”时，不为此单独创建持久决定。纯机制说明归设计属主，规范性行为归产品合同，修订过程按各属主规则记录。

新 ADR 默认使用 `status: proposed`；只有决定获得明确批准后才改为 `accepted`。决定撤回或被取代时，保留原编号为存根并标记 `deprecated` 或 `superseded by ADR-NNNN`。

仅在存在未被“反悔成本”或“权衡”涵盖的重要非显然后果时，添加“后果”一节。
